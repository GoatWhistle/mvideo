# API

> HTTP API бэкенда стенда: 6 методов под префиксом `/api/v1`. Спецификация OpenAPI генерируется
> из кода и руками не пишется; из неё же генерируются типы фронтенда. Ошибка у всего API одна по
> форме: машинный `code` и `message` для логов.

**Читайте, если** вы интегрируетесь с решением или проверяете права доступа · **Связано:**
[архитектура](architecture.md) · [запуск](running.md)

---

## Где спецификация?

| Что | Где |
|---|---|
| Swagger на запущенном стенде | http://localhost:8000/docs |
| OpenAPI JSON на стенде | http://localhost:8000/openapi.json |
| Типы фронтенда | `frontend/src/shared/api/schema.gen.ts`, пересборка — `cd frontend && npm run api:types` при запущенном бэкенде |

У каждого метода в спецификации — описание, схемы запроса и ответа и перечень кодов ошибок.

## Как устроены вход и права?

Входа и ролей нет: стенд — одна страница в одном рабочем пространстве без регистрации
([ADR 0005](adr/0005-stand-scope.md)). Очередь проверки общая для всех, кто открыл стенд.

## Как выглядит ошибка?

Тело ошибки одно на весь API:

```json
{
  "code": "review_already_resolved",
  "message": "Review item is already resolved"
}
```

`code` — машинный код: фронтенд показывает текст из своих словарей по ключу `errors:api.<code>`.
`message` — по-английски, для логов и разработчиков; в интерфейс не попадает.

| Статус | Когда |
|---|---|
| 404 | Записи нет |
| 409 | Действие недоступно в текущем состоянии |
| 422 | Запрос не прошёл проверку схемы или правил |
| 503 | Данные стенда не собраны |

| `code` | Статус | Когда |
|---|---|---|
| `validation_error` | 422 | Пустое название, слишком длинные поля, неизвестное действие |
| `unknown_category` | 422 | Категории нет в пакете стенда |
| `invalid_correction` | 422 | Исправление без значения |
| `review_item_not_found` | 404 | Значения с таким `id` нет в очереди |
| `review_already_resolved` | 409 | Значение уже принято или исправлено |
| `stand_unavailable` | 503 | Бэкенд запущен без пакета `STAND_PACK` |

## Какие есть разделы?

### Служебное

| Метод | Путь | Что делает |
|---|---|---|
| GET | `/api/v1/health` | Проверка живости процесса для Compose |

### Стенд

| Метод | Путь | Что делает |
|---|---|---|
| GET | `/api/v1/stand` | Дата сборки пакета, порог уверенности и категории с их обязательными атрибутами |
| GET | `/api/v1/examples` | Примеры карточек из `test`: название, описание, атрибуты продавца, категория |
| POST | `/api/v1/extract` | Извлекает атрибуты карточки: по каждому — значение, уверенность, источник, цитата и её смещения `start`/`end` в поле `text`; значения ниже порога получают `status: "review"` и `review_id` и попадают в очередь; `missing` — обязательные атрибуты без значения |
| GET | `/api/v1/review` | Очередь проверки; `?status=pending|accepted|corrected` фильтрует, ожидающие идут первыми |
| POST | `/api/v1/review/{item_id}` | `{"action": "accept"}` или `{"action": "correct", "value": "..."}`: решение сохраняется алиасом «цитата → значение», и следующее извлечение той же карточки возвращает это значение с уверенностью 0,97 и источником `review` |

## Как меняется контракт?

Несовместимое изменение выкатывается в три шага: фронтенд понимает обе формы → бэкенд переходит на
новую → старая форма удаляется. Типы фронтенда пересобираются из OpenAPI в том же изменении, где
меняется API.
