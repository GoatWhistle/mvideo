# План валидации

> Как проверяется качество извлечения атрибутов: на каких данных, какими метриками, с какими
> базовыми линиями и какие значения считаются хорошими. План зафиксирован **до первого прогона**
> базлайна и меняется только записью в журнале в конце файла. Отчёт собирает одна команда,
> отрицательные результаты публикуются рядом с положительными.

**Читайте, если** вы хотите понять, почему числам в README можно верить, или проверить, не подогнана
ли проверка под решение · **Связано:** [доказательства](evidence.md) · [ограничения](limitations.md) ·
[архитектура](architecture.md)

---

## По каким правилам идёт проверка?

1. **План фиксируется до результатов.** Версия плана для первого прогона — содержимое этого файла
   в коммите, который его добавил; этот коммит предшествует первому прогону базлайна на реальных
   данных, дата фиксации — дата коммита.
2. **Любая правка — только записью в [журнал](#журнал-изменений):** дата, что было, что стало,
   причина и видели ли мы результаты по этой метрике.
3. **Настройка отделена от оценки.** Справочники, частоты значений по категориям и профили
   атрибутов строятся только по сплиту `train`. Пороги и веса эвристик, если подбираются, — только
   на `val`. Метрики считаются на `test` и `new_category`, где ничего не настраивается.
4. **Истина отделена от признаков.** Эталон — параметры каталога `*_search`; во вход карточки они не
   попадают (тест подготовки данных `test_split_offer_keeps_search_params_out_of_card_input`). Бренд и модель в
   эталоне — поля `vendor` и `model` оффера, во вход они тоже не попадают.
5. **Отрицательный результат публикуется как есть,** с разбором причины.
6. **Одна команда собирает отчёт:** `cd backend && uv run baseline --data ../data/processed
   --out ../data/predictions --reports ../reports` пишет `reports/baseline.json` и
   `reports/baseline.md`. Отчёт руками не правится; повторный прогон на тех же данных даёт тот же
   файл: сплиты заданы сидом подготовки данных, в коде базлайна случайности нет.

## Как сравниваются значения?

Предсказание и эталон приводятся к каноническому ключу. Для числовых атрибутов (≥80% значений
эталона — число с единицей) сравнивается число: «6,7"» и «6.7» совпадают, «256Гб» и «256 ГБ» тоже.
Для остальных — текст после нормализации: нижний регистр, «ё» → «е», пробелы, разделители «/»,
формы и английские названия базовых цветов («черная», «black» → «черный»). Синонимы вне этого
списка («графитовый» ≠ «серый») считаются ошибкой.

## С чем сравниваем?

| Базовая линия | Что это | Почему именно она |
|---|---|---|
| B0 | Только атрибуты продавца, перенесённые как есть | Так каталог заполнен без нашего решения |
| B1 | Базлайн: справочники + правила, лучший кандидат по эвристике | Честная нижняя планка, которую должны побить ранжировщик и decision-модель |

| B3 | Ступень выбора: decision-модель TypeSafe Jev выбирает среди кандидатов B1 и значений справочника | Проверяет, что даёт модель выбора поверх правил и сколько это стоит |

B0 и вклад следующих ступеней считаются в абляции; этот план задаёт метрики для всех ступеней.

**Как проверяется B3.** Платные вызовы, поэтому на выборках: настройка — только на `val` (D3),
итог — один прогон на выборке из D1 + D2 с замороженными настройками. Выборка детерминирована:
карточки с наименьшим `sha256(seed:sku_id)`, сид 42; меньшая выборка вложена в большую. На выборке
B3 сравнивается с B1 на тех же карточках. Параметры, подбираемые на `val`: какие слоты отправлять в
модель, сколько вариантов из справочника добавлять, порог переопределения значения B1 и порог
«не указано», при котором значение B1 снимается. Правило выбора порогов: максимум micro F1, при
равенстве — максимум взвешенного F1 (M4). Калибровка вероятностей модели — reliability-диаграмма по
10 корзинам и ECE на парах с эталоном.

## Какие метрики и пороги?

Если не сказано иное, метрика считается на D1 и повторяется на D2.

**M1. Precision, recall, F1 по каждому обязательному атрибуту.** На парах с эталоном: TP —
предсказание совпало с эталоном; FP — предсказание есть, но не совпало; FN — эталон есть, а
верного предсказания нет (неверное предсказание — одновременно FP и FN). Предсказания на парах без
эталона не входят в precision: отсутствие `*_search` не означает, что атрибута нет у товара; их число
публикуется отдельно («лишние заполнения»). Агрегаты: micro (сумма по всем парам) и macro (среднее F1
по атрибутам, у которых ≥20 пар с эталоном). **Порог для B1:** micro F1 на D1 не ниже 0,5; бренд —
F1 не ниже 0,9.

**M2. Потолок и recall от потолка.** Потолок — доля пар с эталоном, где значение эталона дословно
(после той же нормализации) есть в тексте карточки: заголовок, описание, атрибуты продавца. Recall от
потолка — recall на этих парах. Показывает, сколько упущено из того, что честно можно извлечь с
цитатой. **Порог для B1:** не ниже 0,6.

**M3. Покрытие.** Доля пар «карточка × обязательный атрибут», где значение заполнено: до решения
(у продавца есть атрибут с совпадающим по смыслу названием) и после. **Порог:** покрытие после не
ниже покрытия до.

**M4. Качество с учётом трафика.** M1, где каждая пара весит `weight` атрибута категории из
`required_attributes` (клики категории × доля запросов с упоминанием значения), делённый на число
карточек категории: каждая категория-атрибут вносит вклад по трафику, а не по числу карточек.
**Порог:** публикуется рядом с невзвешенным; расхождение больше 10 п. п. разбирается в отчёте.

**M5. Разрезы.** M1–M3 отдельно для: частых категорий (топ-50 по кликам) и хвоста; D2; смартфонов и
ноутбуков; крупных (≥1000 офферов), средних и мелких (<100 офферов) продавцов. **Порог:** F1 на хвосте
и у мелких продавцов не ниже F1 всего набора больше чем на 15 п. п.

**M6. Цена.** Доля карточек, ушедших в дорогую ступень, и стоимость на 1 млн карточек — для ступеней
с decision-моделью и LLM. У B1 внешних вызовов нет. **Порог:** публикуется рядом с выигрышем.

Уверенность базлайна — эвристическая и **не калибрована**; в файле предсказаний это отмечено полем
`confidence_calibrated: false`. Калибровка (reliability-диаграмма, ECE) — задача ступени ранжировщика.

## Как воспроизвести?

```bash
unzip brief/sources/dataset.zip -d data/raw
cd backend
uv run prepare-data --raw ../data/raw --out ../data/processed
uv run baseline --data ../data/processed --out ../data/predictions --reports ../reports
```

Отчёт — `reports/baseline.md` и `reports/baseline.json`; предсказания по D1 и D2 —
`data/predictions/baseline.predictions.jsonl`, кандидаты для следующих ступеней —
`data/predictions/baseline.candidates.parquet`. Без сети и платных ключей.
