# Эталон — параметры `*_search` каталога, вход — всё остальное

В архиве организаторов нет обещанной «размеченной части» и перечня обязательных полей (ТЗ: стр. кейса,
раздел 6; с. 17). В `skus.pkl` у офферов есть параметры с суффиксом `_search` — нормализованные
значения, на которых работают фильтры каталога. Берём их как эталон: вход пайплайна — `title` и
`description` из `sku_desc.parquet` и параметры продавца без `_search`, цель — значения `_search` того
же SKU. Обязательные атрибуты категории — бренд, модель и самые частые `_search`-поля, ранжированные
по кликам из `query_clicks.parquet`. Допущение до ответа организаторов (вопросы Q2, Q4).

## Рассмотренные варианты

- **Разметить выборку вручную или через LLM:** отклонено как основной путь — за сутки не набрать
  объёма на хвост; остаётся запасным, если пересечение файлов окажется малым.
- **Оценивать только по совпадению с параметрами продавца:** отклонено — продавец и есть источник
  шума, это не эталон.

## Следствия

- Ни одно `_search`-поле не попадает во вход; это проверяет юнит-тест подготовки данных.
- Многие описания содержат блок «Характеристики: • ключ: значение», поэтому метрики считаются в двух
  режимах: с блоком и с вырезанным блоком.
- Если организаторы дадут свой gold-сет, он становится основным, а `_search` — вспомогательным.
